# KVM MicroVM Management – Architecture

**Status:** Draft v0.1 (POC) · **Repo:** Jason-fy-wang/kvm-magement (`kvm-manager`, `kvm-agent`)

> **Note on sources.** This document is based on the repo's top-level layout (`kvm-agent/`, `kvm-manager/`) and the project description. I could not read the code inside the folders, so language/framework choices below are *recommendations*, marked **\[Assumption\]**. Please correct anything that conflicts with the existing agent code.

## 1. Purpose and scope

An internal system to manage microVMs (e.g. Firecracker / Cloud Hypervisor / QEMU microvm) across a small fleet of KVM hosts.

**In scope (POC):**

- VM CRUD: create, list/get, start, stop, delete (update = resize/metadata, limited)
- Status monitoring of hosts (agents) and VMs
- Remote command execution on a host/VM via the agent
- A web UI for all of the above

**Out of scope (POC):** live migration, multi-tenant billing, HA of the center service, advanced scheduling, image registry, SDN beyond a simple bridge/TAP setup.

## 2. Goals and non-goals

| Goals | Non-goals |
| --- | --- |
| Prove the 3-layer flow end to end | Production-grade HA |
| Keep the agent small and dumb; keep logic in the center | Complex scheduler / bin-packing |
| Every operation is async, traceable, and idempotent | Multi-region |
| Know the state of every VM within \~10 s | Sub-second telemetry |

## 3. High-level architecture

```
+-----------+      HTTPS/JSON + WS/SSE      +----------------+     HTTP(S)/gRPC      +-------------------+
| Frontend  | <----------------------------> | Center Service | <------------------> | Agent (per host)  |
| (Web UI)  |                                | (kvm-manager)  |  commands  ->        | (kvm-agent)       |
+-----------+                                |  API + DB +    |  <- heartbeat/events |  VM runtime + cmd |
                                             |  task engine   |                      +---------+---------+
                                             +-------+--------+                                |
                                                     |                                  KVM / microVM runtime
                                                 +---v---+                              (Firecracker etc.)
                                                 |  DB   |
                                                 +-------+
```

### 3.1 Layers and responsibilities

| Layer | Owns | Does **not** own |
| --- | --- | --- |
| **Frontend** | UI, user interaction, display of state, live updates | Business rules, direct host access |
| **Center service** | Source of truth (DB), REST API, auth, node registry, scheduling (pick a node), task orchestration, status aggregation, event fan-out | Talking to KVM directly |
| **Agent** | Local VM lifecycle (calls the existing create function etc.), local resource facts, heartbeat/status reporting, command execution, local cleanup | Global decisions, persistence of cluster state |

**Design principle:** the center holds *desired state*; the agent reports *observed state*; the difference is reconciled by tasks.

## 4. Key design decisions

### 4.1 Center ↔ Agent communication

| Option | Pros | Cons |
| --- | --- | --- |
| **A. Center calls agent API; agent pushes heartbeat/events to center** | Simple, matches "create already works via manual call", easy to curl/debug | Center must reach every agent (fine on an internal network) |
| B. Agent opens a long-lived bidirectional gRPC stream to center | Works through NAT, low latency commands | More moving parts, reconnect logic, harder to debug |

**Decision for POC: Option A**, with the agent API kept small and versioned (`/v1`). The contract is defined so it can move to Option B later without changing the data model.

### 4.2 Asynchronous operations

VM create/start/stop can take seconds. All mutating calls return **`202 Accepted` + `task_id`**. The UI polls or subscribes to the task and VM state. This avoids HTTP timeouts and gives a natural place for retries and audit.

### 4.3 Desired vs. observed state

- `vms.desired_state` is set by the user via center (e.g. `running`, `stopped`, `deleted`).
- `vms.observed_state` is set from agent reports (e.g. `creating`, `running`, `stopped`, `error`, `unknown`).
- A reconciler in the center creates tasks when they differ (POC: only on explicit user action + after node recovery).

### 4.4 Idempotency

Every agent command carries a `request_id` (the task id). The agent stores recently handled ids and returns the previous result on repeat. The VM id is generated by the **center**, so a retried create cannot make a second VM.

### 4.5 Status monitoring

- Agent sends **heartbeat every 5 s** with host metrics and a VM state summary.
- Center marks a node `offline` after **3 missed heartbeats (\~15 s)** and its VMs `unknown` (not `stopped`, because we don't know).
- On agent restart it re-reports all VMs it finds locally, so center can fix drift.
- Frontend gets updates via **SSE/WebSocket**, falling back to polling.

### 4.6 Tech stack **\[Assumption\]**

| Part | Recommendation | Why |
| --- | --- | --- |
| Center | REST service in the same language as the existing code, PostgreSQL (SQLite acceptable for the first demo) | Relational data, simple |
| Agent | Single static binary or lightweight service, runs as a systemd unit, local state in a small dir/SQLite | Easy deploy |
| Frontend | SPA (React/Vue) + a component library | Fast to build tables/forms |
| Contracts | OpenAPI spec for center API; OpenAPI or protobuf for agent API | Generate clients, avoid drift |

## 5. Data model (center DB)

| Table | Key fields |
| --- | --- |
| `nodes` | id, name, address, status (`online/offline/draining`), agent\_version, cpu\_total, mem\_total\_mb, disk\_total\_gb, last\_heartbeat\_at, labels |
| `vms` | id, name, node\_id, desired\_state, observed\_state, vcpus, mem\_mb, disk\_gb, image, kernel, ip, mac, created\_at, updated\_at, last\_error |
| `tasks` | id, type (`create_vm`, `start_vm`, `stop_vm`, `delete_vm`, `exec`), target\_id, node\_id, status (`pending/running/succeeded/failed/timeout`), params (json), result (json), error, created\_by, created\_at, finished\_at |
| `node_metrics` (optional, short retention) | node\_id, ts, cpu\_pct, mem\_used\_mb, disk\_used\_gb |
| `audit_log` | id, user, action, target, ts, detail |
| `users` (POC: one admin / static token) | id, name, token\_hash, role |

## 6. VM lifecycle

```
            create           boot ok            stop
 (none) ---------> creating ---------> running ------> stopped
                      |                   |   ^           |
                      | fail              |   | start     | delete
                      v                   v   +-----------+
                    error <-------------- error          v
                      |                                deleting --> (gone)
                      +-------- delete ------------------^
```

Any state may become `unknown` when the owning node is offline; it returns to the real state after the next successful report.

## 7. Core flows

### 7.1 Create VM

1. UI → `POST /api/v1/vms` (name, vcpus, mem, disk, image).
2. Center validates, **selects a node** (POC: first online node with enough free resources), inserts `vms` (`creating`) and `tasks` (`pending`), returns `202 {vm_id, task_id}`.
3. Task worker calls agent `POST /v1/vms` with `request_id`.
4. Agent runs the create routine, replies quickly (accepted) or when done (POC: synchronous with timeout is acceptable).
5. Agent reports the VM state in the result and in the next heartbeat; center sets `observed_state=running`, task `succeeded`.
6. UI sees the change via SSE/poll.

### 7.2 Start / stop / delete

Same pattern; center changes `desired_state`, creates a task, agent executes, observed state flows back.

### 7.3 Heartbeat and monitoring

Agent → `POST /api/v1/agent/heartbeat` every 5 s: node facts, metrics, list of `{vm_id, state, pid, uptime}`. Center updates `nodes`, diffs VM states, emits events.

### 7.4 Execute command

UI → center `POST /api/v1/nodes/{id}/exec` (or `/vms/{id}/exec`) → task → agent runs with timeout and output cap → result stored in task. See the Agent doc for safety rules.

## 8. Interfaces (summary)

Full detail lives in the component docs.

- **Frontend ↔ Center:** REST `/api/v1/...` + SSE `/api/v1/events`.
- **Center → Agent:** REST `/v1/...` on the agent port.
- **Agent → Center:** `POST /api/v1/agent/register`, `POST /api/v1/agent/heartbeat`, `POST /api/v1/agent/events`.

**Common error format:** `{ "code": "VM_NOT_FOUND", "message": "...", "request_id": "..." }`.

## 9. Security

| Concern | POC approach | Later |
| --- | --- | --- |
| User auth | Static admin token or simple login + JWT | SSO/OIDC, RBAC |
| Agent ↔ center auth | Pre-shared bearer token per node, issued at registration | mTLS with short-lived certs |
| Transport | TLS if possible; at minimum a trusted internal network | mTLS everywhere |
| Command execution | Disabled by default; allowlist or admin-only; timeout + output cap; fully audited | Per-role policy |
| Agent privileges | Runs as a dedicated user with only the access needed for KVM/TAP/disk paths | Further sandboxing |
| Input validation | Strict validation of names, paths, sizes at both center and agent (never build shell strings from input) | – |

## 10. Observability and operations

- Structured JSON logs with `request_id` / `task_id` / `vm_id` / `node_id` in every line.
- Basic Prometheus-style `/metrics` on center and agent (optional in POC).
- Health endpoints: center `/healthz`, agent `/healthz`.
- Config via file + env; agent needs only the center URL, node token, and data dir.

## 11. Failure handling

| Failure | Behavior |
| --- | --- |
| Agent unreachable during a task | Task retried up to N times with backoff, then `failed`; VM marked `error` or `unknown` |
| Agent crashes mid-create | On restart it scans local VMs and reports; center reconciles (adopt, or mark `error` + allow delete) |
| Center restarts | Pending/running tasks are reloaded from DB; heartbeats rebuild live state |
| Node offline | Node `offline`, VMs `unknown`; no new VMs scheduled there |
| Duplicate request | Deduplicated by `request_id` |

## 12. Risks and open questions

1. Which microVM runtime does the existing create function use (Firecracker, QEMU microvm, other)? This affects the state-probing code in the agent.
2. How are images/kernels/rootfs distributed to hosts (pre-baked vs. pulled)?
3. Networking model: bridge + TAP with static IP pool, or DHCP? Who allocates IPs?
4. Does "update" mean resize (requires restart) or only metadata for the POC?
5. Expected scale (nodes / VMs) – affects DB choice and heartbeat cost.
6. Is command execution needed *inside* the guest (needs guest agent/vsock/SSH) or only on the host?
